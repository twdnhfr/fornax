# Changelog

## 1.1.0 — unreleased

- **Peers — every server a host** (`peers:` in `fornax.yaml`, off by default): the fleet repo lies on every server, and `fornax --on <server> <command>` runs plan, apply or any other command there, with your login key forwarded for that run only — servers hold no keys to each other. Every commit must be signed by one of `peers.signers`, checked against the signers of the commit before it; your machine pins the state it trusts (`fornax peers trust`) and refuses older or forged histories. Changes made on a host are committed there, signed through your agent, and come back checked; one that changes what trust rests on (signers, logins, hosts, secret sources) waits for `peers sync --accept-trust-changes`. Only the login key is forwarded (a key without a touch of its own asks before each use), hosts check other servers against the host keys you know, and no connection outlives its run. A run goes on when the connection drops (`peers attach`). New: `peers trust`, `peers verify`, `peers status`, `peers sync`. ([peers](docs/peers.md))
- **`fornax health` checks what listens against the firewall config:** ports opened in `firewall.allow` count only for their protocol, port ranges count, and SSH is expected on the server's own port. Ports Docker publishes (docker-proxy, or a DNAT rule in its `DOCKER` chain, also without the userland proxy) are critical — ufw does not filter them — unless `firewall.allow` opens them on purpose. NTP (123/udp) joins DHCP as expected. ([safety](docs/safety.md))

## 1.0.1 — 2026-10-24

- **fornax is public.** `self-update` downloads releases over plain HTTPS — no GitHub CLI needed any more; it stays the way in for a private fork. Trust still comes from the signature, never from the channel. The README installs with `curl`.

## 1.0.0 — 2026-10-24

From this release on, fornax keeps what [compatibility](docs/compatibility.md) lists within 1.x: the config format, commands and options, `--json` output, error and exit codes, permission tiers and the layout on servers.

- **`fornax server convert <server> --only <modules>`:** hands a server taken over from Forge to fornax module by module (base, access, security, web, php, data). It reads the server first and keeps what fornax would otherwise change unasked — time zone, reboot time, PHP's default version and php.ini, installed tools, ufw rules, Redis without a password, the CrowdSec bouncer already there — then switches the modules on; the plan afterwards shows only what fornax changes on purpose. `--dry-run` shows it without writing. Panel files that clash with fornax's own (a `conf.d/gzip.conf` setting what fornax's nginx.conf sets, an apt source of a repo fornax manages under another name, channel or mirror — two of those break every `apt update`) go into the new `retire` list. Tried on two production servers taken over from Forge.
- **New server keys:** `php_ini` (php.ini settings over fornax's defaults), `retire` (taken-over files fornax's own replace, backed up by the apply), `firewall.allow` entries on a network interface (`on: tailscale0`).
- **Only this machine:** memcached listens on 127.0.0.1 and ::1, like MySQL and Redis.
- **Security review** of everything since 0.1.0, each finding checked by a second pass: ufw opens a server's own `ssh.port` (a per-server port was ignored — bootstrap would have locked SSH out); `public_ipv4`/`public_ipv6`, `ssh.user`, a site's `php` and `php_default` are validated (`php_default` must be one of the server's versions); `site check` runs openssl without a shell, keeps every request on the site's name and strips control characters from what servers send back; `site add` puts the server file back when the fleet refuses the site; repo detection reads https and local repos only; prerelease versions order correctly (rc.10 after rc.9).
- **Release signing hardened:** the key is usable only from `v*` tags (a GitHub environment), signing runs in a job of its own after the build, actions are pinned by commit; manual dry runs stay unsigned.
- **`docs/config.md` describes every key.**

## 0.2.0 — 2026-10-24

- **Exit codes, frozen for 1.0:** 0 done and ok, 1 done but not ok (a result: `health` with a warning or worse, a failed deploy, `diff`/`dns status`/`env diff` with differences, …), 2 an error. `run` and `shell` keep the exit code of the command on the server and exit 255 on fornax's own errors, as ssh does. Before: errors exited 1 like results that were not ok, `health` exited 2 when critical, and `diff`, `dns status` and `env diff` exited 0 with differences.
- **Option names, frozen for 1.0:** list options are singular — `server add --module`, `--service` (were `--modules`, `--services`; the plural keeps working for every list option). `server create --ssh-key` (a public key for root) is now `--authorized-key`: `--ssh-key` always means the private key fornax logs in with.

## 0.1.0 — 2026-10-24

First version, tested on OrbStack machines and on Hetzner Cloud servers.

- **Updates:** `fornax self-update` installs the newest release (or `--version x.y.z`) after checking `SHA256SUMS` against the release key (Ed25519, signed in CI) and the archive against `SHA256SUMS`; `--check` only asks. A note once a day says when a newer release is out. Servers are ordered by version first, then build stamp, so an apply never puts an older release on a server. `requires: ">=x.y.z"` in `fornax.yaml` refuses older fornax (`fornax_too_old`). `bun run release <version>` sets the version, dates the changelog, checks, commits and tags.
- **Steps in order:** a plan of single sites on a server fornax never set up is refused with `not_provisioned` and `fornax server provision` as next step; deploy and git connect name provision too when the server is not set up.
- **Sites without a domain:** an IP address is no site name (the error names its sslip.io name); `--preview` without `preview_domain` names the site under the server's IP via sslip.io; names without public DNS get a self-signed certificate.
- **`site add` reads the preset off the repo** (artisan, index.php, a start script, index.html, a build script) and refuses a branch the repo does not have; **`fornax site set`** and **`fornax server set`** change settings without editing YAML. Preset php gets no Redis unless asked (`--redis`). `server add` says how fornax logs in and takes `--ssh-user`/`--ssh-port`; the first site notes databases nobody uses.
- **`site check`:** no HTTPS for `tls: none`, the reason for every `ERR`, `--body`, `--verbose` (timings, certificate names), names the certificate misses; no more `"" 400` lines in the access log. `fornax run <site> df -h` passes `-h` to the command.

- **Node apps (`preset: node`):** Next.js and other apps with their own server run as the site's user behind nginx, which proxies the site's names to them (websockets included); TLS, redirects, aliases, snippets, push-to-deploy, logs, backups and `fornax run` work as for every site. `node.start` is the start command, the build comes from the lockfile (bun or npm) unless `deploy.commands` says otherwise. Deploys stay zero-downtime with the same promise: the new release starts in a second slot (a systemd unit on its own port, 127.0.0.1), must answer before nginx is switched to it (validated reload), and the old slot stops once nginx has finished its requests — a release that does not start never serves, and the live one keeps serving. Rollbacks and changed units take the same path. Measured on an OrbStack VM with a Next.js 16 site under continuous load: 0 failed requests of 8307 across a deploy, 0 of 7246 across a release that crashed at start (not activated), 0 of 2584 across a rollback. Ports are derived from the domain (or `node.port`) and checked against other apps, proxies and the webhook; `config_invalid` when the server lacks node (or bun). `fornax logs <site> app`, slots in `fornax explain`.
- **Deploys, rollbacks and restarts of a site wait for each other** instead of running at the same time.
- Fixed: `fornax explain <site>` lost its cron and disk facts on sites without supervisor programs.

- **What 1.0 promises** ([compatibility](docs/compatibility.md)): the fleet config format, command names and options, `--json` output (fields are only added), error codes, exit codes, the permission tier of each command and the layout on servers stay compatible within a major version. Fixed before promising it: `-h` is `--help`, and help never fails on the arguments around it; `fornax help <command>` and `--help --json` (the command as data), `fornax server --help` lists the group, `fornax server` alone names its subcommands; global options may come before the command; short flags and switch values like `--json=maybe` are errors instead of a site name or `true`, an empty number is no longer 0; an error after `--` (`fornax run … -- cmd --json`) is no longer printed as JSON; a bad server name is `invalid_argument` everywhere (`import forge` crashed with an internal error); `fleet push` without `fleet_copy` is `no_fleet_copy`. Commands that edit a fleet of an older config version (`site add` on a server file with `hook_domain`) no longer fail, and `apply` no longer downgrades fornax on a server that runs a newer build.
- **Releases and reference:** every tagged release has archives for macOS and Linux (arm64, x86_64) with the Linux builds fornax puts on servers, `SHA256SUMS` and a Homebrew formula ([install](README.md#install)). Every key of the fleet config, with type, default and meaning, is in the [configuration reference](docs/config.md), generated from the schema.
- `server destroy` of a server already deleted in the provider's panel cleans up after it (tailnet, host keys, fleet, 1Password) instead of failing; a 404 from a provider's API is `provider_not_found`. `keychain:` references outside macOS say the Keychain is macOS only.

- **A local dashboard: `fornax ui`.** A web page on 127.0.0.1 for humans: the fleet at a glance (from the config, no SSH), server status, health, certificates, backups, releases and logs on demand, a new site → its plan → apply after a confirmation, plan and deploy per server and site. Every button runs the same command as the CLI, in-process through the command registry — same validation, tiers, errors and output; long commands stream their log, including "touch your security key". No destroy-tier commands, and plans that delete things are left to the terminal. Secured by a random token traded for an HttpOnly SameSite=Strict cookie, a `Host` check against DNS rebinding and a custom header on every POST; nothing is loaded from the internet; it stops after 30 minutes without requests ([docs/ui.md](docs/ui.md)). Notices that went straight to stderr (security key touch, Tailscale login, config notes) now go through one sink, so the dashboard shows them with the run that caused them.
- **Renamed from `anvil` to `fornax`** (anvil clashes with Foundry's binary next to its `forge`). Servers set up under the old name move over in one full `plan` + `apply`: state, secrets, keys and deploy history are copied (never regenerated — restic key, webhook secrets and deploy keys stay the same), files that would clash are renamed, old units and files are removed afterwards, the backup repository on the Storage Box is renamed with its snapshots, the 1Password item is renamed. Webhooks under `/anvil/hook/…` keep working and `git connect` moves them to the new path; `anvil.yaml`, `.anvil/deploy.sh` and `$ANVIL_*` build variables are still understood. Commands refuse a server that has not moved yet (`legacy_layout`). Create steps now check again at apply time and never replace what exists by then.

- **Security review** (threat model and limits in [SECURITY.md](SECURITY.md)): root no longer acts inside a site's home — directories, `.env`, `auth.json`, deploy keys, `env pull|push`, log reads, `git` and release deletes run as the site user, so a symlink a compromised app plants cannot reach root's files. Deploy and daemon logs moved to `/var/log/fornax-sites/<user>/` (root-owned; old deploy history is moved on the next apply, links left behind). Site users can no longer be system, database or admin accounts, and accounts below UID 1000 are never taken over or deleted; two sites can no longer share a database name. Fleet values get strict checks (host names, branch, repo, cron, program names, paths, sizes) and no line breaks outside free text. Generated vhosts have `disable_symlinks if_not_owner`. The deploy config on the server is readable by root and the webhook only; webhook requests yield only a commit id; a failed sudo no longer leaves the staged script behind; `keychain:` references work for heartbeat, ntfy token and composer auth.

- **Config version 2, frozen:** `fornax.yaml` carries `version: 2`; unknown keys anywhere are errors instead of being ignored. Older configs load as upgraded (with a note), `fornax fleet upgrade` writes the upgrade (and renames `anvil.yaml`) and changes only the lines that change — comments and layout stay; a config newer than fornax fails with `config_too_new`. Later breaking changes come as upgrade steps, never as a silent change of meaning. Version 2 renamed: `hook_domain`/`hook_port` → `webhook: { domain, port }`, a site's `keep_releases` → `deploy.keep_releases`, `notify.url` → `notify.webhook`.
- **`fornax server rename <server> [new-name]`:** a new name everywhere — hostname on the server, the name at Hetzner, the machine (and MagicDNS) name in the tailnet, `servers/<name>.yaml`, the 1Password item, the backup repository on the Storage Box. The old name is kept as `former_names`: snapshots made under it stay listed, restorable and pruned with the new ones (restic keeps the host a snapshot was made on).
- **Tailscale API** (`tailscale.api_token`): a single-use auth key per new server instead of a stored reusable one, key expiry turned off for servers, the device removed when the server is destroyed and renamed when it is.
- **How a server got to where it is — `fornax history <server>`:** every server keeps /etc in git (etckeeper, `history: true` by default; keys and secrets stay out of it). fornax commits around each change it makes — "outside fornax: …" for whatever changed since the last commit, then "fornax: …" with the plan, the fleet commit and who ran it — and etckeeper adds package updates and a daily commit by itself. So `fornax history web-1 --path ufw` answers "who changed the firewall, and when": fornax, a package, or someone by hand; `--show <commit>` gives the diff, and changes not attributed yet are listed as such. No second record of the configuration: the fleet repo says what should be, the server what is, its git log how it came about.
- **The tailnet policy from the fleet** (`fornax tailnet status|sync`): your own devices reach everything; machines at home (`tailscale.home`, tag:home) too, and may SSH to the servers; internet-facing servers (tag:server) reach only the tailnet's DNS servers and what `tailscale.allow` lists, and SSH nowhere — a compromised app stays on its server. fornax writes acls, ssh, hosts and its tags, keeps the rest of the policy, saves the previous one, and tags the machines. New servers join tagged. Found in a security review: untagged, a server counted as one of your devices — and with a "my devices may SSH as root to my devices" rule, any app on any server was root on every machine of the tailnet. ufw cannot help there: tailscaled accepts tailnet traffic before ufw sees it.
- **Push-to-deploy through each site's own domain:** GitHub posts to `https://<site>/.well-known/fornax-hook` — the name already points at the right server, so no webhook hostname per server, no DNS record, nothing to forward. The webhook runs wherever a site deploys; the location lets the push past the site's basic auth and IP rules (rules made with `if … return` in a snippet need the path added). `webhook.domain` is optional now. `fornax git connect` checks the URL with a signed ping first (it deploys nothing) and only then points GitHub at it, moving the site's hook from an older URL instead of adding a second one.
- **`redirects:` on a site:** names that only send visitors on to the site's domain (301, path kept, http and https in one hop) — another TLD of the brand, an old name. They are in the certificate and in `dns sync`.
- **Write commands never change a fleet nobody pointed at:** outside a fleet repo, read commands still fall back to `~/.config/fornax/fleet`, but write and destroy commands refuse (`implicit_fleet`) unless the fleet is named (`--fleet`, `$FORNAX_FLEET`) — and every write names the fleet it changes. `server bootstrap` says how logging in works afterwards; `site add` names the TLS default and what each preset serves, takes `--web-dir`, and gives one next step (provision for a server's first site, plan otherwise — the dashboard follows it). Fixed: a site's basic auth or IP gate made the pre-activation health check of PHP sites fail with 401/403.
- **A first setup an agent gets right on its own** (tested: a fresh agent with nothing but the CLI set up a site on a bare Ubuntu box): `fornax init --ssh-key <file|reference>` sets the login key (without it, `fornax.yaml` shows how, commented), init makes the fleet a git repo and calls `secrets setup` optional; a refused SSH login says which key was offered and where to set another; `server add --services` chooses what provision installs, and server add says what that is; provision ends with the first `fornax deploy` of each site; site add says when plan + apply is right and when provision; `agent-context` spells out the order of a first setup.
- **Commands work from any directory:** outside a fleet repo fornax uses `$FORNAX_FLEET`, or `~/.config/fornax/fleet` when it exists.
- **The fleet repo on its servers, encrypted (`fleet_copy`):** after every apply the server keeps the fleet repo with its history, encrypted to age recipients (hardware keys through age-plugin-fido2-hmac, a paper key) and signed with the fleet's SSH key. `fornax fleet restore <dir> --from root@… --signer … --identity …` brings it back on a machine that has nothing else, taking the newest copy whose signature holds — a copy a broken-into server made up is refused. `fornax fleet copies` lists them, `fornax fleet push` stores them now. A failed copy warns and never fails the apply.
- **`fornax shell <site>` and `fornax run <site> -- <command>`:** work as a site's user without giving it an SSH login — root comes in (with the security key: the same open connection) and drops to the user, in the site's directory, with `php` the site's PHP version. `run` streams the output, has no stdin and exits with the command's exit code.
- **Root only with a hardware key:** `ssh.root_keys` sets root's `authorized_keys` exactly (nothing else stays in it; a server's own `ssh.root_keys` are added), entries may carry options such as `verify-required`, `tailscale.ssh_server: false` turns Tailscale SSH off so sshd with those keys is the only way in as root (switched off a few seconds after the apply, which may be running over Tailscale SSH; refused without `root_keys`). `ssh.security_key` points at a FIDO2 key handle (`ssh-keygen -t ed25519-sk -O resident -O verify-required`): fornax asks for the PIN and announces the touch with macOS dialogs, and keeps one connection per server open for `ssh.keep_open` (default 10m) so a whole run needs one touch per server; a cancelled PIN or a missed touch is reported as such (`security_key`), not as an unreachable server. Needs an ssh with FIDO support (Homebrew's openssh; Apple's has none). `tailscale.ssh_check` (default 12h) and `tailscale.tag` are configurable. Fixed: `~/` in `ssh` paths was resolved inside the fleet directory.
- **Network checks in `fornax health`:** per server, what listens beyond localhost apart from nginx, SSH and Tailscale (warning) and what a scan of its public addresses from where fornax runs finds open besides 80/443 (critical); fleet-wide, servers without their tailnet tag (critical) and a tailnet policy that differs from the fleet's (warning).
- **Security updates when a server is set up:** `server create` installs them after provisioning (and reboots if they need it), `server bootstrap` installs them too — a provider's image is often dozens of updates behind.
- **Preview names under a domain of your own:** with `preview_domain` in `fornax.yaml` (a domain whose subdomains reach your servers, e.g. through a wildcard record), `fornax site add <server> --preview` names a site for you (`quiet-harbor.<preview_domain>`) and `fornax site alias <site> --preview` gives an existing one such a name — instead of a provider's throwaway domains. `fornax site alias` also adds and removes names by hand and says when the vhost or certificate would not cover them yet.
- **Expiring credentials are announced:** whenever fornax uses a secret from 1Password whose item carries an expiry date (the "valid until" field of API credentials, or a date field named like it), it warns from 14 days before (`onepassword.warn_expiry_days`) — once per item and run, on stderr, never failing the command. `fornax health` adds a fleet-wide "credentials" check: warning when one is due, critical once one has expired.
- **Recycled names no longer lock fornax out:** a server reached under a new name (its tailnet name after `create`, a new name after `rename`) keeps the host key already seen for it, replacing whatever a destroyed server left under that name; `destroy` and `rename` clear the names and addresses they give up.
- **Restores in quick succession** no longer clash: restore directories and databases are stamped to the second (and counted on).
- **Server names made up for you:** `fornax server create` without a name picks two words like Forge does (`silent-comet`, `roaming-glacier`), never one used in the fleet or at the provider.
- **`server create` from nothing to provisioned:** one SSH key per fleet (`ssh.key`, made by `fornax secrets setup` as an SSH key item that 1Password generates; fornax holds it in an ssh-agent of its own — never a key file, never Touch ID), delete protection at Hetzner (`server destroy` lifts it), provisioning in the same run (`--no-provision` stops once the server is reachable). With `access: tailscale`: joins the tailnet with `tailscale.auth_key` (over SSH, never through cloud metadata), switches `host` to the tailnet name, checks Tailscale SSH works, and only then lets the firewall close the public SSH port; the fleet key comes off the server afterwards. Bootstrap no longer locks a Tailscale server out (the tailnet comes before the firewall) and joins it with the auth key instead of stopping. `server destroy` logs the machine out of the tailnet.
- **`fornax secrets setup`:** one command gives a fleet its own 1Password vault and a service account limited to it (token in the macOS Keychain or a 0600 file), and turns on copying credentials after every apply — no Touch ID prompts afterwards. `fornax init` points to it as the next step. The copy now also covers the sites' deploy keys and the Storage Box key; values that came from the fleet config (ntfy token) are no longer copied back.
- **A Redis of its own for every PHP site** (`redis.instance: own`, the default): a `redis-server` per site that runs as the site user and listens only on a unix socket in a directory of that user (`/run/fornax-redis/<user>/redis.sock`) — no other site reads its cache, sessions or queues, and `cache:clear` (FLUSHDB) only empties its own. `redis.maxmemory` (default 256mb; keys with an expiry give way first, queues never). New sites get the socket in their `.env`; sites adopted from Forge stay on the shared Redis (`redis.instance: shared`), static sites get none, and `redis.instance: none` says a site uses no Redis at all.
